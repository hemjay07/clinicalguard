# ADR-020: UI v1.1 — Multi-Condition Authoring, Expanded Landing, Design System

**Date:** 2026-06-15
**Status:** Accepted

## Context
The v1.0 authoring UI (ADR-019) shipped and is live. Three gaps surfaced after
deployment. First, the authoring flow forced single-condition cases, even though
`eval_cases.condition_ids` is already a JSON array — real clinical cases
routinely span multiple conditions. Second, the landing page understated the
framework, positioning it as NSTG-specific when the architecture is
guideline-agnostic, and not communicating the three-layer design or the roadmap.
Third, the aesthetic was default-Tailwind generic, which undersold the work for a
project intended to signal serious engineering.

## Decision
Three focused changes, none requiring a schema migration.

**Multi-condition authoring.** `POST /api/v1/eval-cases` accepts a `conditions`
array (each entry a `{condition_id, subtype}` pair); all referenced conditions
are validated to exist. The stored `expected_response` blob gains a `conditions`
list and an array-valued `derived_from`; the case body itself stays singular
(one query, one diagnosis set, one set of tier categories). List and detail
endpoints return all referenced conditions. The frontend condition picker becomes
a multi-select with per-condition subtype; the authoring page shows a tabbed
source panel (one tab per condition) over a single unified form, and aggregates
the verified safety rules across all selected conditions.

**Expanded landing page.** An eight-section, content-first landing page using
verbatim copy: hero, "why this matters" (citing Korom et al. 2026 / Penda Health
and the NOHARM benchmark with verified figures), the three-layer framework
description (guideline / safety / context), current status with live stats,
roadmap (Phases B–E plus the context layer), resources, and a footer. A new
`/eval-dashboard` placeholder page documents the Phase D dashboard, with a nav
entry added for it.

**Design system.** IBM Plex Serif (headings), Sans (body), and Mono (identifiers);
a deeper forest-green primary with a muted gold accent and warm-gray neutrals
replacing the default cool slate; nav active-state as an underline rather than a
filled block; subtle borders over shadow-cards. Tailwind theme customization only
— no framework change, components refined rather than rebuilt.

A `LICENSE` file (MIT) is added so the public repository is genuinely
open-source rather than implicitly all-rights-reserved.

## Consequences
Multi-condition support matches how clinicians actually frame cases and uses the
data model as it was already designed; the singular case body keeps scoring
unchanged. Storing the per-condition references inside the existing
`expected_response` JSON avoids a migration, consistent with ADR-019, at the cost
of those references not being independently queryable in SQL.

The landing page now reflects the framework's depth and is honest about what is
implemented (guideline + safety layers) versus roadmapped (context layer, eval
dashboard), which matters for a methodology paper that will be read critically.
All external claims are backed by cited sources with verified figures; no
statistics are fabricated.

The design system is a presentation change only and carries no architectural
risk; it can be iterated without touching application logic.
